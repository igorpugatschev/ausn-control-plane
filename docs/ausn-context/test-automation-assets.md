# Активы автоматизации ПК АУСН

## Назначение оценки

Исторические репозитории `ausn-qa-project` и `codexcli-ausn` используются как источник
подходов, сценариев и заготовок. Они не являются актуальной конфигурацией стенда и не
изменяются. Перед повторным использованием каждый контракт сверяется с актуальными
требованиями, исходниками через Сократ и фактическим поведением стенда Агророс.

## Что можно переиспользовать

| Область | Найденный актив | Практическая ценность |
| --- | --- | --- |
| REST API | `HttpClient` на `httpx`, настройки через окружение, Pydantic-модели ответов | Основа функциональных, негативных и контрактных проверок UC |
| Kafka | `KafkaCategorizerClient` для RedPanda Console API: публикация, опрос результата, корреляция с БД | Основа проверки входных/выходных топиков и правил категоризатора |
| БД | Сессионный клиент и read-only проверки состояния | Проверка асинхронных эффектов REST/Kafka и подготовка безопасных предусловий |
| Данные | Уникальные ИНН/UUID, фикстуры-владельцы данных, cleanup в `finally`/finalizer | Изоляция прогонов и снижение загрязнения общего стенда |
| Наборы | REST UC01–UC24, Kafka/categorizer, integration, tooling, characterization | Исходная регрессионная таксономия, которую нужно сверять с текущими контрактами |
| Отчётность | Allure, JUnit, pytest markers, QA-ledger и отчёты по задачам | Воспроизводимые доказательства и трассировка сценариев |
| Ручные активы | Markdown-кейсы, схемы Kafka, Postman как вторичный слой | Быстрый старт исследовательских и диагностических проверок |

## Ограничения исторической реализации

- Значения по умолчанию относятся к прежнему контуру `192.168.20.18`; применять их к
  текущему стенду нельзя.
- Общий `Settings` допускает переопределение из `.env`, но Kafka session fixture содержит
  прежний URL RedPanda напрямую. Этот разрыв устраняется в `ausn-control-plane`, не в
  репозитории разработчиков или историческом QA-репозитории.
- Kafka-клиент рассчитан на HTTP API RedPanda Console. Совместимость его endpoint и формата
  сообщений с текущей Console проверяется отдельным безопасным probe.
- Исторические статические идентификаторы и банковские реквизиты не переносятся; нужны
  синтетические уникальные значения либо разрешённые данные, полученные во время прогона.
- Characterization-набор полезен как снимок прошлого поведения, но широкие наборы
  HTTP-статусов или `404` не являются product oracle без актуального контракта.
- Полноценной UI-автоматизации для текущего `iframe-test.html` не обнаружено. UI пока
  покрывается браузерным исследованием, затем — собственным набором control plane.
- Tooling и позитивные интеграционные сценарии могут менять стенд. Их запуск только opt-in,
  с подтверждённым владением данными, correlation ID и очисткой.

## Готовность каналов

| Канал | Текущее понимание | Что проверить перед первым прогоном |
| --- | --- | --- |
| REST | Каркас и сценарии пригодны к адаптации | Base paths, авторизация по ИНН/JWT, OpenAPI и допустимость мутаций |
| Kafka | Есть публикация/чтение через Console, ожидание результата и сверка с БД | Endpoint Console, сериализация, топики, права produce/consume и корреляция |
| UI | Основной вход — Агророс через `iframe-test.html`, авторизация по ИНН | Роли/ИНН, маршруты, селекторы и связь UI с REST/Kafka |

## Правило переноса сценария

1. Сохранить бизнес-намерение и инвариант сценария.
2. Заново получить актуальный контракт из первичного источника.
3. Заменить адреса, идентификаторы, payload и ожидаемые статусы актуальными значениями.
4. Отделить базовый сценарий Агророса от банковской адаптации.
5. Для записи обеспечить уникальную корреляцию, владение данными и cleanup.
6. Сохранить доказательства без секретов: запрос/сообщение, ответ, topic/partition/offset,
   trace/correlation ID, состояние БД и релевантные логи.
