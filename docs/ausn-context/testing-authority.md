# Полномочия и источники данных для тестирования

## Разрешённые действия

Пользователь разрешил тестовые мутации на тестовом стенде Агророс:

- REST API: изменяющие запросы;
- Kafka: отправка и чтение тестовых сообщений;
- UI: действия, изменяющие тестовые данные;
- административные и tooling-сценарии.

Разрешение действует только для тестового стенда и не распространяется на production,
репозитории разработчиков, реальные пользовательские данные или внешние интеграции вне
границ тестового сценария.

## Источник тестовых данных

Актуальные тестовые данные и параметры авторизации получать во время прогона из локальной
конфигурации проекта автотестов и доступных источников стенда. Значения секретов, токенов,
ИНН и персональных данных не копировать в Git, отчёты или постоянный контекст.

Проект автотестов определяет роли и состояния как минимум для:

- зарегистрированных ИП и ЮЛ;
- незарегистрированного ИП;
- `BOUND_BANK_CLIENT`;
- `EX_BANK_CLIENT`;
- административного пользователя.

Авторизация REST использует настроенные токены и заголовки `Authorization` и
`X-Client-Data`. Конкретные значения берутся из окружения непосредственно перед запросом.

## Безопасность мутаций

- Сначала фиксировать исходное состояние и контракт ожидаемого изменения.
- По возможности создавать уникальные синтетические ИНН, UUID и correlation ID.
- Перед использованием синтетического ИНН проверять отсутствие записей в связанных БД.
- Созданные сущности удалять, изменённые — восстанавливать из снимка даже при падении теста.
- Позитивные сценарии tooling и общих данных запускать последовательно и opt-in.
- Kafka-ответ искать только по собственным идентификаторам: `id`, `traceId`,
  `operationDocId`, `operationIdempotencyKey` или `documentId`.
- Сохранять topic, partition, offset и correlation/trace ID, но не полный секретный payload.
- Не использовать тестовую мутацию, если невозможно доказать принадлежность данных тесту
  либо безопасно восстановить состояние.

## Kafka-контур из проекта автотестов

Исторический клиент поддерживает публикацию через RedPanda Console API, чтение сообщений,
ожидание коррелированного ответа и последующую проверку БД. Среди покрытых семейств:

- операции и категоризация;
- отмена операций;
- ККТ/FD;
- отчёты НДФЛ;
- смена налогового режима;
- синхронизация налогоплательщиков;
- отвязка партнёра;
- уведомления.

Имена топиков, endpoint Console и схемы сообщений каждый раз сверять с текущим стендом.
Значения старого контура `192.168.20.18` запрещено использовать как актуальные.

## Критерий готовности конкретной задачи

Перед изменяющим прогоном должны быть определены: актуальный контракт, собственные
тестовые данные, наблюдаемый результат, способ корреляции, процедура cleanup и граница
допустимого воздействия. Отдельное повторное разрешение пользователя не требуется, если
все действия остаются внутри этих ограничений тестового стенда.
