# Карта системы ПК АУСН

## Назначение

ПК АУСН — банковская микросервисная платформа для работы банка как информационного партнёра ФНС в режиме АУСН. Основные функции: подключение налогоплательщиков, управление правами и привязкой партнёра, получение и категоризация операций, налоговые процессы и отчётность, интеграция с ДБО банков и административное сопровождение.

## Компоненты

| Компонент | Роль в системе | Основные границы риска |
|---|---|---|
| `ausn-core` | Доменные процессы и интеграция с ФНС | асинхронные ответы, статусы, идемпотентность, подпись, повторная обработка |
| `ausn-categorizer` | Категоризация банковских операций | правила категорий, повторная категоризация, объём и порядок операций |
| `ausn-front-module` | Backend-for-Frontend клиентского кабинета | согласованность с core, буфер операций, права и представление статусов |
| `ausn-front-gateway` | Профильные адаптеры банков/ДБО | различия профилей, контракты банков, аутентификация и деградации |
| `ausn-dbo-integration` | Интеграция с ДБО по REST | пагинация, повторные запросы, неполные/дублированные данные |
| `ausn-admin-backend` и dashboard | Административные операции и диагностика | RBAC, опасные restart/tooling-действия, аудит, раскрытие технических данных |
| `ausn-frontend` | Банковские клиентские приложения и общие пакеты | межбанковые варианты, совместимость общего ядра, UI/API-контракты |
| `ausn-api` | API-контракты | рассинхронизация generated-кода и реализаций при API-first миграции |

Платформа использует Kafka для событийного обмена, отдельные PostgreSQL БД сервисов, Keycloak для аутентификации, криптографический сервис для подписания и Graylog/Prometheus для наблюдаемости.

## Критические сквозные потоки

1. Постановка налогоплательщика на АУСН → подтверждение ФНС → обновление профиля → привязка информационного партнёра → отражение прав в кабинете.
2. Получение операции из ДБО → публикация в Kafka → категоризация → сохранение/отображение → подтверждение обработки банку.
3. Изменение или отмена операции → корреляция с исходной операцией → асинхронный ответ → согласованное состояние во всех сервисах.
4. Формирование НДФЛ-отчёта → расчёт → отправка → приём/отказ ФНС → отображение итогового статуса.
5. Отвязка партнёра → событие/ручной процесс → обновление core и front-module → ограничение доступных действий.

## Модель стендов

- `test1` — текущий trunk (`develop`), ранняя интеграционная проверка.
- `test2` — релизный поезд `stream/X.Y.x`, приёмка prerelease/hotfix.
- `infra` — общие Kafka, PostgreSQL, Prometheus, Keycloak, DSS и документация.
- `demo` — демонстрационные/эмуляционные компоненты; не считать эквивалентом тестового контура без отдельной проверки.

На дату снимка test2 в основном использует `stream/1.10.x`, но административные и некоторые вспомогательные компоненты развёрнуты из `develop`. Это нарушает простую модель «один стенд — один релизный состав» и требует явной матрицы версий.
