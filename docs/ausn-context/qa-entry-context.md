# QA-вход: риски и подготовка к тестированию

## Оценка готовности

Текущее решение QA: **условно готово к ограниченному smoke и исследовательским проверкам, но не подтверждено как готовое к полной регрессии или релизному sign-off**.

Основания:

- среда доступна технически;
- точный состав test2 смешанный и не связан формально с deployment-ревизиями;
- QA pipeline не проходит свой quality gate;
- один из основных frontend pipeline недавно падал;
- активные изменения затрагивают сквозные процессы, данные и контракты;
- операционные сигналы ещё не превращены в воспроизводимые дефекты.

## Приоритеты риска

| Приоритет | Риск | Почему важен | Первое доказательство |
|---|---|---|---|
| P0 | Несогласованность состава test2 | результат нельзя однозначно отнести к релизу | матрица сервис → image tag → commit → branch |
| P0 | Расхождение состояний core/front-module при bind/unbind и миграции | может дать неверные права и доступ пользователю | согласованность сущностей и событий на одной синтетической цепочке |
| P0 | Потеря/дублирование/зависание операций | влияет на налоговый учёт и ресурсы сервиса | Kafka correlation + БД трёх сервисов + Graylog |
| P1 | Ошибки RBAC/admin tooling | административные действия могут раскрыть данные или менять процессы | матрица ролей для чтения, export и restart; destructive вызовы не выполнять без отдельного разрешения |
| P1 | Рассинхронизация API-first контрактов | клиенты и сервисы могут собираться, но быть несовместимыми | consumer/provider contract smoke по опубликованным спецификациям |
| P1 | НДФЛ: расчёт, шаблоны и статусы | финансовая корректность и сложная статусная модель | oracle на суммы/округление + переходы статусов и отказы ФНС |
| P1 | Неработающий quality gate QA-проекта | снижает доверие к автоматизированному вердикту | чистый pipeline после отделения lint от продуктовых проверок |
| P2 | Недостаточная наблюдаемость UI/DSS | `up` не покрывает пользовательский и криптографический контур | синтетический smoke с trace ID и проверкой метрик/логов |

## Обязательная разведка перед тест-кейсами

1. Получить у владельца релиза цель проверки: `develop`, `1.10.x`, `1.11.0` либо конкретный hotfix.
2. Зафиксировать фактическую матрицу версий test1/test2 и исключения смешанного состава.
3. Прогнать недеструктивный smoke: auth, health, чтение ключевого API, Kafka round-trip на специально подготовленных данных, доступность зависимостей.
4. Согласовать безопасные синтетические налогоплательщики и операции. Реальные ИНН из логов/чатов не использовать.
5. Выбрать один сквозной сценарий и вести единый evidence pack: вход, trace/message/operation IDs, ответы API, записи БД до/после, логи, метрики и ожидаемая модель состояний.
6. Уточнить ожидаемое поведение для двух свежих сигналов: очистка `categorized_buffer_operation` и сверка запрошенных/выданных прав.
7. До использования результата автотестов отделить инфраструктурный/линтерный статус pipeline от продуктовых assert-результатов.

## Definition of Ready для полноценного цикла

- названы релиз и scope;
- известны версии всех участвующих компонентов;
- тестовые данные разрешены и восстанавливаемы;
- критерии ожидаемых состояний согласованы;
- observability позволяет связать запрос, событие и запись БД;
- известные блокирующие дефекты привязаны к scope;
- автоматизация либо зелёная, либо её ограничения явно исключены из вердикта.
