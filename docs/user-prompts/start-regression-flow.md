# Предрелизный прогон регрессии (release scope, read-only)

Назначение: фактическое предрелизное регрессионное тестирование ПК АУСН без правок — найти
функциональные дефекты до релиза.

Источник истины: навык `ausn-qa-loop` (режим `regression-audit` для аудита и запуска наборов;
изменения кода в этом прогоне запрещены), правила — корневой `AGENTS.md`.

Подставьте свои значения: `<СПИСОК ЗАДАЧ>` или `<VERSION>`/ссылка на релиз в Jira.

```text
/goal Используй $ausn-qa-loop в режиме regression-audit для фактического предрелизного регрессионного
тестирования ПК АУСН.

Релиз: <ссылка на релиз или fixVersion, например https://jira.rocketscien.se/projects/PKAUSN/versions/<ID>>

Цель: найти функциональные дефекты до релиза.

Порядок:
1. Выполни preflight: SocratiCode codebase_status для ausn-control-plane и ../ausn/ausn-ai; gitlab health;
   test_pgdb list; test_graylog get_current_time; Grafana datasources health; test_ssh list_servers.
   Недоступное зафиксируй с fallback. Продуктовые репозитории — read-only (git pull --ff-only);
   watcher индекса не останавливать.
2. Получи задачи релиза в статусе Done через Jira (JQL: project = PKAUSN AND status = Done AND
   fixVersion = "<VERSION>" ORDER BY key ASC). Jira — граница выборки и traceability; структура прогона —
   по устойчивому функционалу.
3. Найди и запусти существующие автотесты затронутого функционала: сначала REST, затем Kafka, при
   необходимости — UI (Python + Playwright через CDP). Номера Jira не использовать в именах, маркерах и
   командах запуска.
4. Проведи triage каждого падения: product_bug, test_bug, test_data_issue, environment_issue, flaky,
   contract_conflict или unknown. Падение без воспроизведения и evidence дефектом продукта не считать.
5. После релизного набора запусти остальную доступную функциональную регрессию ПК АУСН: стабильные
   REST/Kafka-наборы, применимые smoke/integration-проверки и UI-проверки по потребности.
6. Работай read-only: не меняй код, тесты, данные и документы; не создавай коммиты; не выполняй push и
   external-write.
7. Для каждого подтверждённого product_bug назначь Severity S1–S5 и укажи рекомендованный Priority P1–P4
   со статусом «Предварительный».
8. Явно перечисли незапущенные проверки и причины.

Ограничения:
- Expected behavior — только из подтверждённого контракта (SocratiCode/OpenAPI/Confluence/GitLab/БД/
  локальные read-only исходники). Jira — provenance, а не структура набора.
- UI-автотесты допустимы на Python + Playwright (CDP); разведка UI и доказательства — через MCP playwright.
- Не публиковать отчёты и комментарии в Jira/GitLab/Mattermost без отдельного approval: текст готовит агент,
  публикует пользователь.

Definition of Done:
- Определён полный scope релиза (Done-задачи, итоговый JQL, полный список).
- Запущены релевантные существующие наборы; по каждому — фактический результат прогона.
- Каждое падение классифицировано; по product_bug собраны шаги, стенд, версия/commit, время UTC,
  доказательства в БД/логах/метриках.
- Для подтверждённых дефектов указаны Severity S1–S5 и предварительный Priority P1–P4.
- Прогнана остальная доступная функциональная регрессия; незапущенные проверки перечислены явно.
- Итоговый отчёт со сводкой (всего/пройдено/упало/skipped, дефекты по severity) и остаточными рисками.
```
