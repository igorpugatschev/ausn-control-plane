# Предрелизный аудит покрытия (Done-задачи релиза)

Назначение: пройти по задачам текущего релиза в статусе Done и определить, покрыты ли связанные
требования актуальными автотестами; закрыть пробелы через ежедневный QA-TASK-FLOW.

Источник истины: навык `qa-loop` (режимы `regression-audit` и `single-feature`) и его
`ausn-control-plane/.agents/skills/qa-loop/references/qa-task-flow.md`, `ausn-control-plane/.agents/skills/qa-loop/references/loop-ledger-schema.md`, `ausn-control-plane/.agents/skills/qa-loop/references/loop-quality-gates.md`;
правила — корневой `AGENTS.md`. Подставьте `<VERSION>`/ссылку на релиз.

```text
/goal Используй $qa-loop в режиме regression-audit для контроля полноты автоматизированного покрытия
задач релиза ПК АУСН в статусе Done.

Релиз: <ссылка на релиз или fixVersion, например https://jira.rocketscien.se/projects/PKAUSN/versions/<ID>>

Цель: повторно пройти по готовым задачам релиза и определить, покрыты ли связанные требования
существующими pytest-автотестами. Если задача уже покрыта — зафиксируй доказательства и не создавай
дубли. Если автоматизация была пропущена — выполни полный ежедневный QA-TASK-FLOW по тем же правилам,
что и для новой задачи.

Перед релизом каждая Done-задача должна быть:
- подтверждённо покрыта актуальными автотестами;
- либо обработана через QA-TASK-FLOW, если автоматизация была пропущена;
- либо явно классифицирована как manual-only с обоснованием, почему автоматизация невозможна.

Выполни PRE-RELEASE AUTOMATION COVERAGE FLOW:

0. Preflight.
0.1. Проверь MCP-окружение: SocratiCode codebase_status для ausn-control-plane и ../ausn/ausn-ai;
     gitlab health; test_pgdb list; test_graylog get_current_time; Grafana datasources health;
     test_ssh list_servers. Недоступное зафиксируй с fallback.
0.2. Проверь актуальность исходников ПК АУСН: продуктовые репозитории в ../ausn обнови только через
     git pull --ff-only; локальные изменения не сбрасывай. ../ausn — только для актуализации и
     read-only анализа.
0.3. Проверь индексы SocratiCode для релевантных проектов; обновляй только при необходимости.
     Watcher — активен, пока SocratiCode работает, останавливать не требуется: он завершается вместе с сервером.
0.4. Если SocratiCode недоступен — зафиксируй fallback на GitLab MCP и точечное чтение файлов.

1. Определи полный состав релиза.
1.1. Граница выборки — переданные Jira-фильтр, доска или релиз.
1.2. fixVersion → JQL:
     project = PKAUSN AND status = Done AND fixVersion = "<VERSION>" ORDER BY key ASC
1.3. Включай только Done (Готово). Не включай In Test, Open, Reopened, To Do, задачи других релизов
     и всё, что вне переданной границы.
1.4. Для каждой задачи зафиксируй: key, summary, description, acceptance criteria, status, issuetype,
     fixVersion, components, labels, parent/subtasks, issuelinks, attachments, comments, ссылки на
     Confluence и GitLab, resolution и resolutiondate.
1.5. Зафиксируй границу релиза, итоговый JQL, общее количество Done-задач и полный список.

2. Классифицируй каждую задачу.
A. API / backend / integration / Kafka / БД — автоматизируемо через pytest.
B. UI — автоматизируемо через Python + Playwright (подключение по CDP к запущенному браузеру).
C. Mixed — есть и серверная, и UI-часть: автоматизируем обе; UI-часть фиксируй отдельным набором.
D. Non-functional / не требует автоматизации — документационное, инфраструктурное или техническое
   изменение без проверяемого продуктового контракта.
Правила: не придумывать проверку там, где контракт не подтверждён; для mixed разделять серверные и
UI-результаты; manual-only допустим только с явным обоснованием невозможности автоматизации.

3. Определи устойчивый функциональный scope: сгруппируй задачи по функциональным областям;
Jira — provenance и traceability, не структура тестов.
Номер Jira запрещено использовать в имени файла, класса, теста, в pytest-маркере, pytest.ini,
allure feature/story/title и как единственный критерий регрессионного запуска.

4. Найди источник expected behavior: SocratiCode, OpenAPI, Confluence, GitLab, схемы и данные БД,
   локальные исходники в ../ausn (read-only), Jira — если в ней есть требование или ссылка на первичный
   контракт. Если источник отсутствует, конфликтует или неоднозначен — не создавай тест на основании
   предположения; зафиксируй BLOCKED или DONE_WITH_CONCERNS с указанием, какого источника не хватает.

5. Проведи аудит существующей автоматизации.
5.1. Найди относящиеся к функционалу pytest-тесты, fixtures, фабрики данных, API-клиенты, Kafka-сценарии,
     проверки БД, pytest-маркеры, UI-тесты, Postman-сценарии и записи ledger.
5.2. Ищи не по номеру Jira, а по API endpoint, Kafka topic, consumer flow, названию операции, сущности БД,
     устойчивому UC, компоненту, бизнес-поведению и функциональному маркеру.
5.3. Сопоставь требования с assertions. Наличие похожего теста покрытием не является. Проверь: покрывает ли
     тест конкретное поведение, актуальны ли assertions, релевантна ли конфигурация, есть ли тестовые данные,
     проходит ли тест на текущем стенде, не skipped/xfail/закомментирован ли он.
5.4. Назначь статус покрытия:
     AUTOMATED_COVERED — все автоматизируемые требования подтверждённо покрыты актуальными тестами;
     AUTOMATED_PARTIAL — покрыты частично;
     AUTOMATION_MISSING — релевантных автотестов нет;
     UI_AUTOMATABLE — UI-часть покрываема Python + Playwright (CDP) и требует реализации;
     MIXED — покрыта серверная часть, UI-часть требует отдельного набора;
     MANUAL_ONLY — проверка возможна только вручную по обоснованной причине;
     NOT_APPLICABLE — продуктовая автоматизация не требуется;
     BLOCKED — невозможно определить контракт или доказать покрытие.

6. Подтверди существующее покрытие для AUTOMATED_COVERED: перечисли пути к тестам и функции, сопоставь
   требования с assertions, выполни релевантные тесты, зафиксируй фактический результат; дополнительные
   тесты не создавай. Задача считается покрытой только при подтверждённом контракте, конкретном сценарии,
   релевантных assertions, необходимых данных и успешном актуальном прогоне (либо явно обоснованном
   ограничении запуска).    Postman не считать достаточным основным доказательством без pytest-теста. Для каждой задачи, признанной
   покрытой (включая покрытые продуктовыми тестами разработчика: они принимаются как evidence, если напрямую
   проверяют требуемое поведение), проверь трассируемость в Zephyr Scale — кейс должен существовать и быть
   привязан к задаче; недостающие догрузи (`zephyr_import_pack` → `zephyr_import` → `zephyr_link_cases`) и
   зафиксируй прогон (`zephyr_automation`).

7. Для статусов AUTOMATED_PARTIAL, AUTOMATION_MISSING, UI_AUTOMATABLE и MIXED (непокрытая часть)
   выполни ежедневный QA-TASK-FLOW: режим single-feature, маршрут contract-research-agent →
   test-design-agent → test-implementation-agent → review-agent; при падениях подключай ci-triage-agent.
   Для каждой задачи: найди и зафиксируй контракт; определи автоматизируемые требования; спроектируй
   сценарии по устойчивому функционалу; повторно проверь покрытие; создай или обнови ledger; подготовь
   данные; реализуй только отсутствующие pytest/fixtures/UI-сценарии; выполни проверки и post-fix retest;
   проведи независимый review.
   Меняй QA-код только в ../ausn/ausn-qa-project, ветка задачи — от актуального main; commit и push
   выполняются сразу после проверок. Один функциональный тест или параметризованный набор может покрывать
   требования нескольких задач — дубли не создавай. Данные создавай в setup/fixture, изолируй, делай
   прогон независимым от предыдущего состояния.

8. Обработай UI-задачи: реализуй UI-автотесты на Python + Playwright через CDP там, где это даёт
   устойчивую проверку; разведку и доказательства веди через MCP playwright; для MANUAL_ONLY перечисли
   требования к ручной проверке и подготовь краткий checklist. Для MIXED явно раздели результаты
   автоматизированных (API/Kafka/БД и UI) и ручных проверок. Если evidence ручной проверки отсутствует —
   не объявляй задачу проверенной перед релизом.

9. Создай или обнови ledger по устойчивому функционалу
   (../ausn/ausn-qa-project/docs/reports/qa-loop-<scope>-<date>.md). Для каждой user story зафиксируй:
   функциональную область, описание поведения, Jira traceability, источник контракта, тип проверки,
   статус автоматизации, путь к тесту, тестовые данные, команду запуска, результат последнего прогона,
   manual-only scope, остаточный риск, итоговый статус (RETESTED_PASS, MANUAL_TEST_REQUIRED,
   DONE_WITH_CONCERNS, BLOCKED).

10. Quality gate для изменённых областей: ruff check, ruff format --check, mypy, pytest --collect-only,
    релевантные функциональные pytest-прогоны, post-fix retest, при необходимости smoke/регрессия и
    audit_gate --full (ожидается 11/11). При падении — systematic debugging, root cause и классификация:
    PRODUCT_DEFECT, TEST_DEFECT, TEST_DATA, ENVIRONMENT, INFRASTRUCTURE, FLAKY. Не подгоняй expected
    behavior под тест.

11. Итоговый self-review: все Done-задачи рассмотрены; нет задач без классификации; для AUTOMATED_COVERED
    есть доказательство; для AUTOMATION_MISSING/UI_AUTOMATABLE выполнен QA-TASK-FLOW или зафиксирован
    блокер; Jira-номера не попали в таксономию тестов; изменения ограничены пробелами покрытия; нет
    секретов и лишних артефактов; временные планы удалены; чужие изменения не перезаписаны.

12. Подготовь матрицу покрытия: Jira | Функционал | Тип задачи | Источник контракта | Статус покрытия |
    Pytest/UI evidence | Результат прогона | Ручная проверка | Итог. Ни одна Done-задача не должна
    отсутствовать.

13. Сводка: всего Done-задач; полностью покрыто; автоматизировано в рамках flow; частично; UI; manual-only;
    not applicable; blocked; дефектов продукта; осталось обязательных ручных проверок; неподтверждённых задач.

14. Предрелизная оценка:
    READY — всё автоматизируемое покрыто и проверено; ручные проверки (если есть) подтверждены; нет
    BLOCKED и критичных дефектов.
    DONE_WITH_CONCERNS — покрытие проверено, но остались явно перечисленные ручные проверки, ограничения
    окружения или некритичные риски.
    BLOCKED — есть Done-задачи без контракта; автоматизируемые задачи без реализованного/проверенного
    покрытия; отсутствует обязательное evidence; недоступен критичный источник или окружение; найден
    блокирующий дефект.
    Не объявляй релиз готовым только по статусу Done в Jira.

15. Записи для журнала учёта времени: общая (аудит Done-задач, проверка полноты покрытия, повторный прогон
    существующих тестов, обработка пропущенных задач, UI-scope, итоговая оценка) и отдельные — по каждой
    пропущенной задаче (Jira traceability, функционал, анализ контракта, реализованное покрытие, данные,
    проверки, результат).

Ограничения:
- Expected behavior — только из подтверждённого контракта.
- Jira — provenance/traceability, не структура набора.
- QA-код менять только в ../ausn/ausn-qa-project (ветка задачи от main; commit и push сразу).
- ../ausn и продуктовые репозитории — read-only.
- Не создавать дублирующие тесты.
- External-write в чужие системы (MR, Jira/GitLab/Mattermost-комментарии) и деструктивные операции —
  только после отдельного approval; текст готовит агент, публикует пользователь.
- При отсутствии или конфликте контракта — BLOCKED или DONE_WITH_CONCERNS.

Definition of Done:
- Получен полный список Done-задач релиза; каждая внесена в матрицу и классифицирована.
- Для существующего покрытия приведено evidence; релевантные тесты повторно запущены.
- Для пропущенных автоматизируемых задач выполнен полный QA-TASK-FLOW.
- Реализованы только недостающие pytest/fixtures/UI-сценарии и тестовые данные.
- Ledger создан или обновлён; выполнены quality gates и post-fix retest.
- Для каждой покрытой Done-задачи (включая продуктовые тесты как evidence) кейс существует в Zephyr Scale
  и привязан к задаче; результат прогона зафиксирован тест-раном.
- Подготовлены матрица покрытия, evidence-based предрелизная оценка и записи для журнала времени.
- Итоговый статус: READY, DONE_WITH_CONCERNS или BLOCKED.
```
