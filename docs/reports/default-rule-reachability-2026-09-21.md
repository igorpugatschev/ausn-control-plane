# DEFAULT_RULE: достижимость и избыточность (вопрос к аналитику)

**Дата:** 2026-09-21
**Источник данных:** `ausn-categorizer` (develop), БД `test1-categorizer.public.rules`, логи пода `ausn-categorizer-1` на test1, прогоны категоризатора.
**Статус:** требуется вердикт аналитика; в автотестах правило помечено `not_testable` и не покрывается.

## Вопрос

Правило `DEFAULT_RULE` (`enabled=true`, `priority=20`, `condition=true`, `markupItems: taxBaseCode=5`) не может быть выбрано ни на одном сообщении. Является ли это логической недоработкой/избыточностью требований — или правило необходимо как страховка?

## Как выбирается правило (алгоритм)

`DatabaseRuleService.applyRule` (`src/main/kotlin/se/rocketscien/integratorcategorizer/service/DatabaseRuleService.kt`):

1. `ruleRepository.findAllByEnabledTrue()` — берутся все включённые правила;
2. для каждого вычисляется условие через **SpEL** (`SpelExpressionParser`); исключение при вычислении = `false` (условие не сработало);
3. выбирается `matchedRules.minByOrNull { it.data.priority }` — **побеждает наименьшее числовое значение `priority`**;
4. если совпадений нет — возвращается `ruleName = null`;
5. разметки с вычисленной суммой `null` или `0` отбрасываются (`mapNotNull`).

## Факты

| # | Факт | Источник |
|---|---|---|
| 1 | `cashFlowDirection` в `OperationDto` — **не-nullable** enum ровно из двух значений: `INCOMING`, `OUTGOING` | `dto/OperationDto.kt` (develop) |
| 2 | `SIMPLE_INCOMING`: условие `cashFlowDirection.name == 'INCOMING'`, `priority=10` | `public.rules` |
| 3 | `SIMPLE_OUTGOING`: условие `cashFlowDirection.name == 'OUTGOING'`, `priority=10` | `public.rules` |
| 4 | `DEFAULT_RULE`: условие `true`, `priority=20`, `taxBaseCode=5` | `public.rules` |
| 5 | Приоритеты: у 99 включённых правил диапазон 1–10; `DEFAULT_RULE` — единственное с 20 | снапшот `artifacts/categorizer-rules-from-db.json` |
| 6 | `DEFAULT_RULE` **сопоставляется на каждом сообщении** и проигрывает по приоритету: в логах `matched rule name='DEFAULT_RULE', priority=20, condition=true` вместе с `matchedRules count=2..4` | логи `ausn-categorizer-1`, test1 |
| 7 | Сообщение с `cashFlowDirection=UNKNOWN` до применения правил не доходит (в логах нет `applyRule`), результат категоризации не формируется | проба через `operation-categorizer.operation-in` |
| 8 | Сообщение с `cashFlowDirection=null` — то же (до применения правил не доходит) | проба |

## Вывод

1. Так как направление всегда `INCOMING` или `OUTGOING` (факт 1), одно из `SIMPLE_INCOMING`/`SIMPLE_OUTGOING` совпадает **всегда** (факты 2–3), и его `priority=10` меньше `20` (факты 4–5). Следовательно `DEFAULT_RULE` **не может быть выбран** ни на одном корректном сообщении.
2. «Неизвестных» направлений в контракте нет: `UNKNOWN`/`null` не доходят до выбора правила (факты 7–8), т.е. как страховка от некорректного направления `DEFAULT_RULE` тоже не работает.
3. Покрытие состояний платёжных поручений **полное без `DEFAULT_RULE`**: «догоняющими» являются `SIMPLE_*` по направлению; при этом условии правило избыточно в текущей логике (факты 6 — оно лишь безусловно участвует в сопоставлении).

## Риски избыточного правила

- Если `SIMPLE_INCOMING`/`SIMPLE_OUTGOING` когда-либо будут отключены, `DEFAULT_RULE` начнёт **молча** проставлять `taxBaseCode=5` (не налоговая база) всем неклассифицированным операциям — это может быть неверно с точки зрения учёта и незаметно в мониторинге.
- Правило с `condition=true` навсегда остаётся в `matchedRules`, создавая шум в логах (DEBUG) и иллюзию действующей страховки.

## Варианты решения (нужен вердикт аналитика)

| Вариант | Суть | Последствия |
|---|---|---|
| A. Оставить как есть | Правило-страховка на случай отключения `SIMPLE_*` | Молчаливая разметка `5`; нужен явный комментарий/документация, что это осознанная страховка |
| B. Удалить/отключить `DEFAULT_RULE` | Убрать избыточное правило | Меньше шума; при отключении `SIMPLE_*` неклассифицированные операции получат `ruleName=null` (сейчас это возможно и допустимо: сервис возвращает пустой результат) |
| C. Изменить семантику «нет совпадений» | Явное «не классифицировано»: `ruleName=null` + алерт/метрика вместо разметки `5` | Прозрачность для эксплуатации; требует согласования с учётной логикой |
| D. Пересмотреть `SIMPLE_*` | Понизить/убрать правила, совпадающие только по направлению | Изменит поведение всех сообщений; возможны новые «дыры» — нужен полный анализ требований |

## Что нужно от аналитика

1. Подтвердить, является ли `DEFAULT_RULE` требуемой страховкой, или это избыточное/устаревшее требование.
2. Если страховка нужна — какая разметка `taxBaseCode` должна проставляться неклассифицированной операции и должен ли быть алерт.
3. Если не нужна — согласовать удаление/отключение правила (вариант B) либо изменение семантики «нет совпадений» (вариант C).
