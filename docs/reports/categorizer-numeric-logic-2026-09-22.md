# Числовая логика категоризатора: нулевые разметки, дроби, большие суммы

Дата: 2026-09-22 · Источник контракта: исходники `ausn-categorizer` (develop, commit `1e21f241`),
`ausn-kafka-contracts` (main), БД `test1-categorizer.public.rules` (снапшот `artifacts/categorizer-rules-from-db.json`),
пробы на test1 (Kafka → `ausn-core.operations`) и SQL по `test1-core`. Jira — только provenance
(повод: вопрос по нулевому возврату в эквайринговом реестре).

## Краткие ответы

| Вопрос | Ответ |
|---|---|
| Нулевые разметки | Отбрасываются **для всех правил** в `DatabaseRuleService.applyRule`: `amount == null \|\| amount.compareTo(BigDecimal.ZERO) == 0` → item не попадает в `specifics`. Итог: правило применено (`ruleName` есть), а разметка отсутствует или неполная. Эмпирика: за 60 дней 0 разметок с нулём/null (они не доживают до БД), но **32 из 35** операций эквайрингового реестра имеют 1–2 разметки вместо 3 |
| Дроби | Выход facade всегда `setScale(2, HALF_UP)`. При разборе из назначения: **точка** — максимум 2 знака, третий и далее **обрезается** (regex), подтверждено пробой (0.125→0.12, 0.129→0.12, 1.999→1.99, 12.345→12.34). **Запятая**: 1–2 знака — копейки, ровно 3 — тысячи, 4+ — дробь с округлением HALF_UP. **Проценты** — любое число знаков, считается корректно (1,234 % от 10 000 → 123.40) |
| Большие суммы | `BigDecimal` на всём пути (DTO `OperationDto.amount`, контракт `SpecificItem.taxBaseAmount`, jsonb `numeric`) — переполнения нет. 94 из 117 объявленных разметок копируют сумму как есть (`#this.amount`) и **сохраняют масштаб источника** (в БД встречаются 0, 1 и 2 знака); facade нормализует к 2 |

## 1. Нулевые разметки

Код (`service/DatabaseRuleService.kt`):

```kotlin
val amount = calculate(operation, item.computation)
if (amount == null || amount.compareTo(BigDecimal.ZERO) == 0) { /* Skip markupItem */ return@mapNotNull null }
```

- Фильтр общий: применяется к каждому объявленному `markupItem` любого правила, до обогащения валютой.
- `compareTo(ZERO) == 0` — сравнение по значению: `0`, `0.0`, `0.00` отбрасываются; **отрицательные — нет**.
- Правило считается применённым даже если все разметки отброшены (`RuleMarkupResult(ruleName, [])`).

Откуда берутся нули (по объявленным разметкам: 117 items, из них 23 facade, 94 `#this.amount`):

| Источник | Поведение |
|---|---|
| `#this.amount` (94 items, 93 правила) | Ноль только если `operation.amount == 0`; масштаб — как в источнике |
| `acquiringCommission` / `acquiringRefund` / `acquiringFixedFee` | `ZERO` при пустом назначении или отсутствии маркеров → item отбрасывается |
| `extractNDSFromPaymentPurpose` | `ZERO` при стоп-словах, «НДС 0 %», отсутствии маркера, `НДС > amount` |
| `amountMinusExtractedVat`, `amountMinusPartialRefundPlusV`, `amountMinusSpecialMarkupPartialBasePlusB*` | Возвращают `ZERO`, если результат < 0 или разметка неприменима → «остаточная» база исчезает |
| `extractPartialRefundPlusVMarkup` / `extractSpecialMarkupPartialBasePlusB*Incoming*` | `null`, если сумма ≤ 0 или > `amount` → соответствующие items = `ZERO` → отброшены |

Эмпирика (60 дней, `test1-core`):

- 6 617 разметок: `null` — 0, ноль — 0 (подтверждает отбрасывание до записи);
- неполные разметки у facade-правил: `ACQUIRING_INCOMING_4_4_1_FNS` — 1 item × 10 ops, 2 × 22, 3 × 3;
  `INCOMING_VAT_SPLIT_4_1_2` — 1 × 29, 2 × 8; `SPECIAL_MARKUP_PARTIAL_*` — 2 (как объявлено);

## 2. Дроби: 1, 2, 3 знака

Округление/масштаб:

- Все вычисления facade завершаются `setScale(2, RoundingMode.HALF_UP)` (комиссия, возврат, полная сумма, НДС,
  «остатки», частичные разметки) → в БД у facade-правил масштаб всегда 2.
- Проценты: `amount * percent / 100` (для /100 деление точное) → затем `setScale(2, HALF_UP)`.

Разбор чисел из назначения (`extractFirstAmount`, приоритет паттернов):

1. `2355 руб. 74`; 2) `197-21`; 3) `0.` (точка-пунктуация); 4) `187.35` (точка, `\d{1,2}`);
5) `1,752` или `554,4` (запятая, любые цифры); 6) целое.

- **Точка, 3+ знака — обрезание, не округление** (паттерн берёт только первые две цифры).
  Проба на стенде: `0.125 → 0.12`, `0.129 → 0.12`, `1.999 → 1.99`, `12.345 → 12.34` (полная сумма и комиссия).
- **Запятая**: `parseAmountOrNull` — если после запятой ровно 3 цифры → разделитель тысяч (`1,752 → 1752.00`),
  иначе дробь (`554,4 → 554.40`); 4+ цифр — дробь, затем `HALF_UP` до 2 знаков.
- `parseAmount` / `parseCommission` (только правило `ACQUIRING`, **отключено**) жёстко ждут `\d{1,2}` и
  берут **первый сегмент** до `", "`; иначе `IllegalArgumentException`.
- Специальные маркеры `+б\d+[.,]\d{2}+` и `+в\d+[.,]\d{2}+` требуют **ровно 2 знака**; иначе разметка
  не применяется (условие false / значение 0).
- `SpecificItemForeignCurrencyAmountEnricher` округляет валютные суммы `HALF_UP` до 2 знаков.

## 3. Большие суммы

- Не найдено мест с `Int`/`Long`/`Double` в денежном пути: `OperationDto.amount: BigDecimal`,
  `exchangeRate`/`foreignCurrencyAmount: BigDecimal`, контракт `SpecificItem.taxBaseAmount: BigDecimal`,
  хранение — jsonb `numeric`. Переполнение и потеря точности в продукте не воспроизводятся.
- Проба (наш клиент): 123 456 789 012 345 678.90 и 987 654 321 098 765 432.10 прошли без ошибок;
  в БД facade-правило записало `...400.00`, `#this.amount` — без нормализации.
  **Ограничение пробы:** тестовый клиент объявляет `amount` как `float`, поэтому >15 значащих цифр
  теряются на нашей стороне; для проверки точности больших чисел нужен сырой JSON (строка) вместо float.
- `amount-ref`-правила не приводят масштаб к 2 знакам: в БД встречаются 0, 1 и 2 знака (6 617 items:
  630 / 5 529 / 458). Для учётных выгрузок масштаб не унифицирован.

## 4. Найденные риски (evidence-based)

| # | Риск | Evidence |
|---|---|---|
| R1 | **Comma-сумма может быть прочитана как чужая дробь.** Паттерн «точка» не привязан к маркеру и ищет первое совпадение по остатку текста. Назначение «… Удерж комисс 1,752 Удерж сумма возв пок-ки 0.00» → комиссия = 0 (взяли `0.00` из хвоста), разметка `taxBaseCode 3` молча отсутствует, полная сумма = `amount` | Проба: markup = [(5, 10000.00)]; в БД только один item |
| R2 | **Третий знак обрезается, а не округляется** (в отличие от процентов, где `HALF_UP`) — асимметрия ожиданий | Проба: 0.125→0.12, 0.129→0.12, 1.999→1.99 |
| R3 | **Исключение в вычислении разметки отменяет применение всего правила** (`ruleName = null`, пустые разметки): внешний `try/catch` в `applyRule`. Пример — `parseAmount`/`parseCommission` (правило `ACQUIRING`, отключено) на 3+ знаках | Код `DatabaseRuleService.applyRule`; риск низкий, пока правило отключено |
| R4 | **Правило применяется с пустой/частичной разметкой** (нет guard «все items отброшены»). Вопрос к учётной логике: операция классифицирована, но базы нет | 32 из 35 операций `ACQUIRING_INCOMING_4_4_1_FNS` с 1–2 items; `INCOMING_VAT_SPLIT_4_1_2` — 29 ops с 1 item вместо 2 |
| R5 | **Масштаб разметки не унифицирован** (facade — 2 знака, `#this.amount` — как в источнике: 0/1/2) | SQL распределения масштаба по правилам |
| R6 | **Отрицательные суммы не отбрасываются** (фильтр ловит ровно ноль) — отрицательная база возможна | Код: `compareTo(ZERO) == 0` |

Примечание: в выборке 60 дней есть 12 items `specifиcs` с `ruleName = null` — операции с разметкой без
применённого правила (вероятно, разметка из другого источника/редактирование); отдельный вопрос, к нулевой
логике не относится.

## 5. Что добавить в автотесты (предложение)

1. `R1`: параметризованный кейс «comma-сумма + точка-дробь в хвосте» для acquiring (сейчас не покрыто).
2. `R2`: фиксация фактического поведения `0.129`/`12.345` как «обрезание» (или баг, если аналитик ждёт округление).
3. `R4`: кейс «все разметки правила нулевые → `ruleName` есть, `markupItems` пуст» — чтобы решение было осознанным.
4. `R6`: кейс с отрицательной суммой (ожидание зафиксировать по решению аналитика).
5. Большие суммы: отправлять payload как сырой JSON со строковыми числами (обойти `float` в тестовом клиенте).
