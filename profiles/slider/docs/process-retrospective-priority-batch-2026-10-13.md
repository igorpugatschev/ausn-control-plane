# Ретро процесса: приоритетная партия задач 12–13 октября 2026

Документ описывает **процесс**, а не продукт: где ушло время, почему вердикты получились медленнее
целевого и что меняется в следующей партии. Оценка скорости — по числу циклов и сборок, а не по
напоминанию о времени: точный учёт активного времени не вёлся, поэтому часы ниже помечены как оценка.

**Статус результатов:** вердикты в работе — slider проверяет мои выводы по 28734 и 28768. Независимо
подтверждено (мой прогон, чужой сценарий): 28734 — дефект сохранения списка после копирования формата.
Выводы по 28820 (корень в `repairs/text.ts`) и 28732 пока опираются на мои сценарии и ждут проверки.

## 2. Куда ушло время (ранжировано)

1. **Портирование чужой тест-обвязки на другую машину — ~10 неуспешных микро-циклов на одну сверку.**
   Это самая крупная статья и она не была плановая:
   - `SSL_CERT_FILE` в `.env` содержит путь macOS (`/Volumes/SliderCS/...`) → httpx падает на
     создании SSL-контекста ещё до тестов;
   - переопределён только `UI_BASE_URL` → API-слой остался на olddev: запись данных ушла туда, а
     браузер смотрел localhost. Симптомы узнаваемы: `Пользователь не в сессии`, `items=0`,
     `ERR_CONNECTION_RESET`; я сначала искал баг в редакторе, а не в адресах;
   - новый тест без записи в `config/test_layers.yaml` роняет прогон целиком (`unclassified`, код 4);
   - модульные фикстуры не видны из другого модуля; `cleanup`-gate блокирует мутирующие тесты после
     неудачной очистки; `-k` по имени функции совпал с параметризованными вариантами.
2. **Стоимость вердикта = стоимость сборки.** На каждую задачу — отдельная пересборка редактора
   (полный build, подмена ассетов, рестарт): в окне партии видно ≥3 сборки. Сценариев на сборку
   мало, поэтому налог платился за каждую задачу, а не за партию.
3. **Дублирование сценариев.** 23 чужих сценария уже лежали в общем `slider-autotests` на ветках
   `codex/qa-*`; я писал свои, пока не сверился. Хуже — мои сценарии опирались на синтетику, а их
   на реальные данные, поэтому мой PASS по 28734 был слабее их FAIL.
4. **Восстановление provenance детективом.** `deploy-receipts.log` обрывается на 2026-10-06, поэтому
   «какой кандидат собран» пришлось доказывать по поведению и по исходникам вместо чтения receipt.
5. **~7 циклов на синтез прекондициона импорта ПСБ** без исходного файла: item-level против
   run-level mark, попытки найти фикстуру в БД. Остановился правильно, но фиксту следовало запросить
   сразу — это единственный способ проверить их FAIL по 28768.
6. **Эргономика машины:** кириллица в stdout нативных процессов и кавычки PowerShell ломали
   однострочники — несколько циклов на «как запустить команду», а не на продукт.
7. **Канал:** первый документ лёг в корень control plane, потому что правила обновились позже моего
   коммита; пришлось переносить (один лишний коммит).

## 3. Три корневые причины

- **A. Пайплайн деплой-ограничен, а не тест-ограничен.** Вердикт стоит столько же, сколько сборка
  кандидата. Пока сценариев на сборку мало, ускорение почти невозможно без группировки задач по SHA.
- **B. Обвязка фактически одномашинная.** Нет документированного контракта «прогон на новой машине»,
  поэтому каждый следующий писатель платит налог заново. Для двух писателей это удвоение стоимости.
- **C. Работа шла последовательно.** Данные slider пришли после того, как я написал свои сценарии.
  Канал работал как отчёт о результатах, а не как планирование: карту «задача → SHA → кто пишет
  сценарий» я не составлял в начале партии.

Отдельно — мой дефект тест-дизайна: **вердикт PASS выдан на сценарии, который не покрывал путь
пользователя.** Кисть применил к уже существующему списку, а баг был в конвертации абзаца в список
после копирования. Зелёный сценарий не доказывает фикс, если путь не покрыт.

## 4. Решения на следующую партию

| # | Решение | Ожидаемый эффект |
|---|---|---|
| D1 | Батчить задачи по SHA редактора: одна сборка → несколько вердиктов; карту «задача → SHA» брать из рапорта в начале партии | снимает основной налог, пропорциональный числу задач |
| D2 | Следующую сборку запускать параллельно с написанием/прогоном текущего сценария (правило «pending build не запрещает независимую подготовку» уже есть — я им не пользовался) | сборка перестаёт быть последовательным этапом |
| D3 | Contract-first: REST/JSON-ассерты до браузера, браузер — только на то, что JSON не доказывает (рендер, фокус, маркеры) | дешевле и быстрее отсеивает неверные сценарии |
| D4 | Reuse-first: `git log --all --grep=<task>` в общем репозитории до написания своего; чужой сценарий запускать дословно | сверка вердиктов становится частью проверки, а не отдельной работой |
| D5 | Контракт переносимости обвязки (одноразово ~30 мин): пара адресов + `TEST_ENV`, CA-переменная, регистрация в `config/test_layers.yaml`, cleanup-gate, `-k` по id | второй писатель и вторая машина стартуют без таксономии |
| D6 | Инструментировать provenance: деплой пишет receipt на каждый запуск (обрыв с 06.10) + `.build-info.json` в `editor-static` | идентичность сборки — чтение файла, а не расследование |
| D7 | Бинарные фикстуры (ПСБ PPTX) — в общий репозиторий или артефакт-хранилище с документированным путём | иначе сценарий непортируем и вердикт невозможно подтвердить |
| D8 | Гейт тест-дизайна: перед написанием сценария — одно предложение «путь пользователя» и отображение каждого оракула на него; путь не покрыт → вердикт не PASS, а BLOCKED | исключает повтор урока 28734 |
| D9 | Эргономика: скрипты файлом вместо PowerShell-однострочников, вывод с кириллицей — в файл | меньше циклов на запуск команд |

## 5. Модель времени на следующую партию

- портирование обвязки: 0 (после D5);
- на кандидат SHA: 1 сборка, параллельно с подготовкой;
- на сценарий: REST ~1–2 мин, браузер ~1 мин;
- на партию из 8–10 задач: ориентир «вердикт = один build-цикл», а не «сборка на каждую задачу».

Оценку этой модели даёт пользователь по следующей партии — это и есть проверка, что ускорение
произошло, а не просто сменился способ работы.
