# AUSN QA control plane

## Назначение

Этот репозиторий — переносимый управляющий проект QA-команды для работы с проектом АУСН.
Все настройки, инструкции и накопленный контекст, необходимые специалисту или AI-модели,
должны храниться внутри этого репозитория и работать после его клонирования на другую машину.
Это репозиторий документации, конфигурации MCP и навыков: в нём нет приложения, сборки и тестов.

Назначение работы: тестирование ПК АУСН и создание/ведение фреймворка автотестов в продуктовом
репозитории `ausn-qa-project` (rcktsci/projects/ausn/integrator/ausn-qa-project) — это продукт работы.
Прежний управляющий проект устарел и ведётся другим специалистом; `ausn-control-plane` создан заново
на новом опыте.

## Модель владения

| Репозиторий | Роль | Запись |
|---|---|---|
| `ausn-control-plane` (этот) | управляющий: правила, навыки, MCP, методология, отчёты | разрешена |
| `ausn-qa-project` | **продукт**: фреймворк и автотесты ПК АУСН | разрешена; commit и push выполняются сразу |
| Продуктовые репозитории разработчиков АУСН, `ausn-ai` | источники контракта и контекста | **только чтение** |

Read-only относится к источникам (код и документация разработчиков), чтобы expected behavior не
подменялся правками; наш продукт — `ausn-qa-project` — создаётся и развивается свободно.

## Обязательные правила

- Мы работаем в роли QA.
- **После приёмки задачи — тест-кейс в Zephyr:** агент пересобирает пакет кейсов из ledger'ов, догружает недостающие в Zephyr Scale, привязывает их к проверенной задаче Jira (панель «Покрытие тестирования») и фиксирует результат прогона тест-раном — инструменты `zephyr_import_pack` / `zephyr_import` / `zephyr_update` / `zephyr_link_cases` / `zephyr_automation` / `zephyr_plan`, порядок в навыке `ausn-qa-loop`.
Кейс в Jira должен отражать текущую автоматизацию: структура папок — `/Автотесты/<Backend · … | Frontend · … | Общее>/<раздел>` (бэкенд и фронтенд разделены, как в ручных кейсах), поле `Компонент` заполняется из справочника проекта (`Фронт-модуль :: backend`, `АУСН-адаптер :: ФНС коннектор` и т.д.), статус переходит `Draft → Approved` только после подтверждённого прогона (`zephyr_update`).
Регресс ведётся **тест-планом** (`zephyr_plan`): план в Zephyr Scale состоит из прогонов (прогон создаётся с `testPlanKey`, состав плана — `traceLinks[].testRun`), слои пирамиды заданы в `data/zephyr/import/layers.json` — `Contract → API → DB/Tooling → Integration → UI/E2E`, каждый слой покрывается прогоном Smoke (priority High) и/или Full. То же правило действует при аудите покрытия: если у принятой Done-задачи кейса в Zephyr нет (в том числе когда покрытие подтверждено продуктовым тестом разработчика) — кейс догружается и привязывается к задаче. **Каждый новый/догруженный кейс обязательно включается в прогоны тест-плана регресса** (`zephyr_plan --layer-runs`, слой по `layers.json`); покрытая задача, чей кейс не входит ни в один прогон плана, закрытой не считается. Эти записи в Zephyr — штатная часть QA-флоу и отдельного approval не требуют; комментарии и публикации в Jira/Confluence/Mattermost по-прежнему выполняет пользователь.
- **Высший приоритет:** работа с файлами связанных проектов (сам control plane и все репозитории в `../ausn`, включая `ausn-qa-project`) ведётся только через SocratiCode по навыку `ausn-socraticode` — поиск, symbol, flow, graph, impact; dot-контент (навыки, субагенты, команды) — через `codebase_context_search`. Прямой обход ФС для связанных проектов не применяется; исключение — неиндексированные проекты.
- Все изменения коммитить и пушить сразу: незакоммиченные и незапушенные правки теряются при потере рабочей копии. Коммит — по завершении логического шага, сообщение описывает суть; **push выполняется сразу после коммита, отдельное разрешение на него не требуется** (решение пользователя 2026-09-18, подтверждено повторно). Отдельный approval нужен только для внешних записей в чужие системы (MR, Jira/Confluence/Mattermost-комментарии) и деструктивных операций.
- **Целевой remote (решение пользователя 2026-10-01):** `ausn-control-plane` пушится **только в личный `github`** (`git@github.com:igorpugatschev/ausn-control-plane.git`); GitLab-remote `origin` для control plane **не используется**. GitLab — только для продукта `ausn-qa-project` (там push идёт в `origin`). Коммиты/мерджи/пуши control plane в GitLab не отправлять.
- Внешние публикации (Jira, Confluence, Mattermost, письма) выполняет пользователь: агент готовит готовый текст для вставки и не публикует его сам. Комментарии через MCP уходят от служебной учётки Rocket.AI и для QA-отчётности не используются (решение пользователя 2026-09-18).
- Не изменять исходники, конфигурацию и историю репозиториев разработчиков.
- Режим только для чтения запрещает собственные правки исходников, но разрешает обновление через Git до remote (`fetch`, `pull --ff-only`). Перед работой проверять актуальность; при локальных изменениях или расхождении веток не сбрасывать их автоматически.
- Тесты, fixtures и тестовую документацию создавать в `ausn-qa-project`; правила, навыки, MCP-конфигурацию и управляющую документацию — в `ausn-control-plane`; прочие артефакты — в папке, явно указанной пользователем.
- Локальные абсолютные пути не считать переносимой конфигурацией. В сохраняемых настройках
  использовать относительные пути, переменные окружения или документированные параметры.
- Если задача требует изменения репозитория разработчиков, остановиться и предложить решение,
  которое размещает изменения в `ausn-control-plane` или `ausn-qa-project`, либо запросить отдельное явное разрешение.
- Секреты держать только в корневом `.env` (в Git не входит). В репозитории есть `.env.example` — шаблон с именами переменных и рабочими корпоративными значениями; личные токены и учётные данные (GitLab/GitHub/Jira) в шаблоне не хранятся и заполняются каждым специалистом самостоятельно (решение 2026-09-24).
  Не записывать токены, Authorization-заголовки и персональные данные в документацию, отчёты и доказательства дефектов.
- Документацию и комментарии вести на русском — сложившаяся конвенция репозитория.

## Работа с кодом

При написании, ревью и рефакторинге кода (тесты, скрипты, правки control plane) применять навык `karpathy-guidelines`:

1. **Сначала думать** — называть допущения и компромиссы, не додумывать молча; при неясности спрашивать.
2. **Сначала простота** — минимум кода, без спекулятивных абстракций и «гибкости на будущее».
3. **Точечные изменения** — трогать только необходимое, подстраиваться под стиль, убирать только свой мусор.
4. **Цель вместо «сделать»** — проверяемый критерий готовности и цикл до проверки.

Детали — в навыке `karpathy-guidelines`; правила `AGENTS.md` и предметные навыки приоритетнее.

## Ретроспектива

По завершении значимой задачи провести ретроспективу сессии и предложить зафиксировать негативные сценарии и их решения в [docs/retrospectives.md](docs/retrospectives.md).

Каждый урок размечается происхождением: `method:<фрагмент базы>` — значит правило в [методологической базе](docs/qa-methodology/README.md) сформулировано слабо, формулировку усилить; `practice:` — правило вне книг, и нужно решить, переносить ли его в навык или в базу. Раз в квартал — свёртка: фрагменты базы, не встречающиеся ни в одной колонке `rule_source`, уходят в `docs/archive/` как справочные, а повторившиеся практические правила становятся правилами навыков.

## Python

- Для запуска любых Python-скриптов и инструментов проекта использовать только локальное окружение `.venv` с Python 3.12.
- В Windows вызывать `.\.venv\Scripts\python.exe`, в Linux/macOS — `./.venv/bin/python` относительно корня проекта.

- Если `.venv` отсутствует, сначала создать его на Python 3.12; не переключаться автоматически на системный интерпретатор.

## Настройка после клонирования

1. Node.js 22+, затем `npm ci --prefix tools/mcp-runtime`.
2. Скопировать `.env.example` → `.env` и заполнить личные токены (GitLab/GitHub); остальные значения — из шаблона.
3. Инфраструктура индекса поднимается автоматически плагином `.opencode/plugin/socraticode.js` (Qdrant на `127.0.0.1:17333`); при отсутствии модели — `ollama pull nomic-embed-text` (Ollama на `127.0.0.1:11434`).
4. Открыть проект из корня и подтвердить доверие к проекту/MCP, если клиент запросит.
5. Если продуктовые репозитории в `../ausn` отсутствуют, агент **клонирует их сам** по `REPOSITORIES.md` (раздел «Первичное клонирование»), не дожидаясь пользователя; клоны — только чтение. GUI-инструменты (Docker, Ollama, VPN), корпоративный плагин opencode и секреты устанавливает/заводит пользователь.

## Конфигурация MCP

- Один и тот же набор серверов (socraticode, atlassian, gitlab, mattermost, test_ssh, test_pgdb, test_graylog, test_grafana, playwright) описан в четырёх файлах: `.mcp.json`, `.codex/config.toml`, `.vscode/mcp.json`, `.opencode/opencode.jsonc`. **SocratiCode работает штатно** (решение 2026-10-01, отменяет «по требованию» от 2026-09-29): сервер всегда подключён, Qdrant/Ollama поднимает плагин `.opencode/plugin/socraticode.js`, контейнер Qdrant закреплён `restart: unless-stopped`. При добавлении или изменении сервера обновлять все четыре.
- Node читает секреты из корневого `.env` через `--env-file`; вручную экспортировать переменные не нужно. Клиенты запускать из корня control plane (актуально и для opencode: в remote-серверах opencode не читать `.env`, авторизация идёт через `mcp-remote` из `tools/mcp-runtime`).
- Кэш авторизации MCP — в `.local/mcp-auth/`. Telegram необязателен и не подключён.
- Источник истины по составу серверов — `configs/mcp/servers.json`; четыре файла сверяются с ним гейтом `.\.venv\Scripts\python.exe tools\checks\mcp_parity.py` (код 1 — дрейф; при расхождении обновить манифест и все четыре). Валидация манифестов — `tools\checks\validate_manifests.py`; единая read-only проверка готовности — `node scripts/bootstrap.mjs --check`.

## Индексация SocratiCode

- Индексируются все репозитории контекста относительно control plane: сам `ausn-control-plane` и все локальные репозитории в `../ausn`, включая `ausn-qa-project`. Это исходники тестируемого приложения и стендовое окружение (`ausn-ai`, `ausn-core`, `ausn-api`, `ausn-front-gateway`, `ausn-frontend`, `ausn-front-module`, `ausn-front-module-api`, `ausn-kafka-contracts`, `ausn-admin-backend`, `ausn-admin-dashboard`, `dbo-emulator`, `test-stands`) и наш продукт `ausn-qa-project` (тесты, fixtures, сценарии — индексируется для удобного ревью и поиска). Индексация не делает репозиторий read-only: `ausn-qa-project` остаётся записываемым, правки автоиндексируются watcher'ом. Новый репозиторий в `../ausn` индексировать по мере добавления. При каждом поиске и обновлении передавать соответствующий `projectPath`; коллекции различаются по пути проекта с префиксом `ausn_qa_`.
- Перед индексацией обновить чистую рабочую копию репозитория через `git pull --ff-only`; локальные изменения не сбрасывать. Эмбеддинги считаются локально, поэтому индексация крупного сервиса идёт десятки минут — выполнять партиями с контролем `codebase_status`.
- **Штатный режим (решение 2026-10-01, отменяет «по требованию» от 2026-09-29):** Qdrant и Ollama работают постоянно — их поднимает плагин `.opencode/plugin/socraticode.js` при старте opencode, контейнер Qdrant закреплён `restart: unless-stopped`. Watcher — часть процесса MCP-сервера: активен, пока SocratiCode работает; отдельной службой не является и останавливать его не нужно. Инструменты `codebase_*` доступны всегда.
- **Границы применимости (урок 137):** семантический поиск («где/как реализовано»), impact-анализ и код-графы — через SocratiCode; поиск по **точному токену/шаблону** — быстрее через `rg`/`ast-grep` по локальному клону, без roundtrip и без расхода токенов на MCP-схему. Для своих репозиториев (control plane, `ausn-qa-project`) работа ведётся напрямую.
- Правило выбора инструментов: индексированные проекты (`ausn-core`, `ausn-ai`, `ausn-control-plane`, `ausn-qa-project` и остальные в `../ausn`) исследуются через SocratiCode, а не прямым обходом ФС.
  - Разведка и незнакомый код — `codebase_search` (гибрид semantic+BM25 за один вызов); читать файлы только после сужения до 1–3 кандидатов.
  - Перед правкой/удалением и при рефакторинге — `codebase_graph_query` / `codebase_impact` (blast radius).
  - Связи функций — `codebase_symbol` / `codebase_symbols` / `codebase_flow`.
  - Dot-контент (навыки, субагенты, команды) — только `codebase_context_search`.
  - Поиск пуст → `codebase_status`, при необходимости `codebase_index`/`codebase_update`.
  - Исключение: точная строка, идентификатор или регэксп — быстрее и точнее через `rg`/`ast-grep` (позиция вендора SocratiCode).
  - Если проект не индексирован — прямая работа с файловой системой.
- Dot-каталоги (`.agents`, `.opencode`) обычный индекс пропускает, поэтому навыки, субагенты и команды подключены как context artifacts (`.socraticodecontextartifacts.json`) и ищутся только через `codebase_context_search` (гибрид semantic+BM25), а не `codebase_search`. Для markdown граф зависимостей (`codebase_graph_*`) пуст — это норма, а не дефект.

## Codemap

- Карта репозитория лежит в самом репозитории — `<repo>/docs/codemap/`; генератор и модели — здесь, в `tools/codemap/`.
- Модель курируется вручную и описывает не более 20 primary-узлов; генератор валидирует пути, считает файлы и фиксирует коммит target-репозитория в `codemap.lock`.
- Регенерация: `.\.venv\Scripts\python.exe tools\codemap\generate.py --all`; проверка актуальности — тот же вызов с `--check` (ненулевой код при устаревшем lock). Обновлять карту вместе со значимым изменением структуры репозитория.
- **Сводная карта системы** (`--system`): узлы — сервисы ПК АУСН (13), инфраструктура и внешние системы; рёбра — `kafka` (по ключам конфигурации), `rest` (конфиг-ключи/порты), `shared-lib`, `auth`, curated. Артефакты пишутся **в продукт**: `ausn-qa-project/docs/codemap/system.{json,html,lock}` + отчёт `docs/reports/system-codemap.md` (код-уровень и вендоренный Cytoscape — рядом). Модель — `tools/codemap/model/system.json`. `--system` вызывается в том же прогоне, что `--all`; гейт — `--system --check` (красный при изменении модели или коммита сервиса; `--allow-stale` смягчает расхождения коммитов).
- **Код-уровень системы** (`--system --parts`): части собираются **локально, вне Git** — `ausn-qa-project/.local/system-graph/parts/*.js`, из графов SocratiCode в Qdrant (`ausn_qa_<id>_symgraph_*`, где `id = sha256(путь проекта)[:12]`); агрегация — до файлов (узлы) и вызовов файл→файл (рёбра). В `system.html` клик по сервису открывает его код-часть. Сервисам без графа нужен `codebase_graph_build` в SocratiCode; отсутствие графа не ломает генерацию и видно в отчёте.
- **Дельта обновления** (`--system`): в отчёте есть раздел «Изменения с прошлого обновления» — сравнение с последним **закоммиченным** `system.json` (история берётся из git, отдельный снапшот не нужен): новые/исчезнувшие узлы и связи, изменения атрибутов (коммит, размеры, генерация графа). Наш продукт (`not_runtime`) из сравнения исключён, иначе каждая выгрузка артефакта давала бы шум.
- Граф связей документации (`--docs`): рёбра из markdown-ссылок, путей в тексте и упоминаний навыков/агентов/команд; кросс-репозиторные цели помечаются префиксом (`<repo>:<path>`). Выход — `docs/codemap/docgraph.{json,html,lock}`.
- Проверки `--docs`: битая относительная ссылка — ошибка; неразрешённый путь внутри `.agents/`/`.opencode/` — ошибка, в остальной документации — warning; документ без входящих рёбер и неизвестные упоминания — warning-списки в отчёте. Регенерация/проверка: `--docs --all` / `--docs --all --check`.
- SocratiCode граф по markdown не строит (ast-grep видит только import/require/export), поэтому связи документации отслеживаются через `--docs`, а не через `codebase_graph_*`.
- Устаревшие документы не удаляются, а переносятся в `docs/archive/` (исключён из сканирования графа и проверок ссылок) с записью в `docs/archive/README.md`; удаление — только по отдельному согласованию.
- Охват сейчас: `control-plane` и `qa-project`. Расширяется добавлением модели в `tools/codemap/model/`.
