# Разработка От Источника

## Правило

Каждое техническое решение должно быть подкреплено источником. Не писать и не менять тест, пока не найден контракт или явно не зафиксирован риск его отсутствия.

## Иерархия Источников

1. SocratiCode по индексированным проектам ПК АУСН.
2. OpenAPI, Confluence, GitLab и схемы БД через корпоративные MCP.
3. Jira — только ссылка provenance/traceability на требования или дефект, но не самостоятельная тестовая таксономия.
4. Локальные исходники `../ausn` в режиме только чтения.
5. Файлы `ausn-qa-project`: существующие pytest-тесты, Postman-коллекции, docs и fixtures.

## Процесс

1. Определи сервис: Core Service, Front Module, categorizer, tooling-controller или другой компонент.
2. Зафиксируй метод, endpoint/topic/table, ожидаемый статус и тело ответа.
3. Найди источник контракта. Если источники противоречат друг другу, вынеси конфликт пользователю.
4. Реализуй тест строго по контракту: статус, тело, Pydantic-валидация, негативные сценарии.
5. Укажи источник в docstring, комментарии рядом с тестом или отдельном поле traceability. `allure.feature`, `allure.story` и `allure.title` описывают только устойчивый функционал и поведение; номер Jira-задачи в них не используется.
6. Запусти узкую проверку, затем релевантный quality gate.

## Конфликты

Если спецификация и реализация расходятся:

- написать тест на ожидаемое поведение;
- пометить `xfail` явным функциональным описанием расхождения; ссылку на Jira при наличии хранить только как источник контракта/дефекта;
- не выбирать удобную версию молча;
- в отчёте указать источник, фактическое поведение и риск.

## Проверка

- Источник контракта найден или отсутствие источника зафиксировано.
- Response body валидируется Pydantic-моделью.
- Ошибки 4xx/5xx проверяются по структуре, а не только по статусу.
- Магические значения объяснены источником.
- Команда проверки и результат указаны в финальном отчёте.

## Откуда правила

- Из базы `docs/qa-methodology/`: `evidence.md#Доказательство` (источник ожидания и оракул; разделение наблюдённого, ожидаемого и непроверенного), `foundations.md#Работа с требованиями` (неясное требование — вопрос, а не выдуманное ожидание).
- Из практики: «202 ≠ успех» для асинхронных методов — итог подтверждается терминальным статусом и результатом (урок 82).
