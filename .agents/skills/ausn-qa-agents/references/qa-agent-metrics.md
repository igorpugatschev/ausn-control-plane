# Метрики агентного QA

## Цель

Метрики агентного QA показывают, улучшает ли агент качество и скорость QA-процесса, а не просто увеличивает количество кода или тестов. Они используются для еженедельного обзора, ретроспективы PR и настройки правил агентов.

Запрещено оценивать успех агентной работы только количеством сгенерированных тестов. Количество тестов имеет смысл только вместе с принятием PR, уровнем ручной доработки, найденными дефектами, flaky/false positive шумом, наличием источника контракта и качеством тестовых данных.

## Источники данных

- GitLab: PR/MR, авторство изменений, статусы review, merge, комментарии ревью.
- `ausn-qa-project`: pytest-тесты, fixtures, markers, история изменений тестов.
- CI: результаты pytest, ruff, mypy, повторные прогоны, длительность падений и triage.
- Jira/Atlassian: дефекты, задачи, связи с PR/MR, escaped defects.
- Postman: вторичный источник, только для сверки синхронизации с pytest.
- Отчёты агента: ссылка на источник контракта, созданные тестовые данные, ручные правки.
- SocratiCode/OpenAPI/БД/документация: подтверждение источников контракта.

## Метрики

| Метрика | Смысл | Источник данных | Периодичность | Формула/подсчёт | Анти-паттерн использования |
|---|---|---|---|---|---|
| `agent_pr_created_count` | Сколько PR/MR создано агентом или при прямом участии агента. | GitLab labels/author, branch prefix, PR description, отчёт агента. | Еженедельно, с месячным трендом. | Количество PR/MR за период с признаком `agent-created` или эквивалентным маркером. | Считать рост этой метрики успехом без учёта merge, доработок и дефектов. |
| `agent_pr_merged_count` | Сколько агентных PR/MR принято в основную ветку. | GitLab merge events, labels/author. | Еженедельно, с месячным трендом. | Количество merged PR/MR из набора `agent_pr_created_count`. Дополнительно считать долю: `agent_pr_merged_count / agent_pr_created_count`. | Давить на merge-rate ценой слабого review или объединять PR без проверки источника контракта. |
| `agent_pr_human_revision_rate` | Доля агентных PR/MR, где человеку пришлось существенно править результат. | GitLab commits after agent handoff, review comments, labels `needs-human-rework`. | Еженедельно. | `PR/MR с существенными человеческими правками / agent_pr_created_count`. Существенная правка: изменение assertions, fixtures, тестовых данных, контракта или архитектуры теста после работы агента. | Использовать как метрику наказания. Высокое значение должно запускать улучшение промтов, ролей, источников и review checklist. |
| `agent_generated_tests_count` | Сколько pytest-тестов добавлено или существенно расширено агентом. | Git diff в `tests/`, pytest node ids, markers, отчёт агента. | Еженедельно. | Количество новых pytest test functions/classes или параметризованных сценариев, созданных агентом. Параметры одного теста считать отдельно только если они покрывают разные бизнес-условия. | Гнаться за числом тестов через поверхностные проверки, дубли, слабые assertions или тесты без данных. |
| `agent_generated_tests_modified_by_human_rate` | Доля агентных тестов, которые человек изменил после генерации. | Git history по тестам, review commits, comments. | Еженедельно. | `Количество агентных тестов с существенными человеческими правками / agent_generated_tests_count`. | Считать любую правку провалом агента. Нормальные правки именования или форматирования не должны портить метрику. |
| `defects_found_by_agent_tests` | Сколько реальных дефектов найдено тестами, созданными или изменёнными агентом. | Jira defects, CI failures, ссылки на test node id и PR/MR. | Еженедельно, с квартальным трендом. | Количество подтверждённых дефектов, где первичный сигнал пришёл от агентного теста. Учитывать только дефекты с подтверждением владельца или заведённой задачей. | Завышать метрику за счёт flaky, окружения, тестовых данных или известных дефектов без новой ценности. |
| `false_positive_failures` | Сколько падений агентных тестов оказалось шумом, а не дефектом продукта. | CI, triage notes, Jira resolution, повторные прогоны. | Еженедельно. | Количество падений за период, классифицированных как ошибка теста, окружения, данных или неверного ожидания. | Скрывать false positive как "нестабильность стенда"; каждый случай должен иметь причину и действие. |
| `flaky_rate` | Доля нестабильных агентных тестов. | CI history, reruns, pytest reports, quarantine markers. | Еженедельно. | `Количество flaky agent tests / количество активных agent tests`. Flaky: результат меняется без изменения кода или данных, либо тест требует повторного запуска для зелёного статуса. | Уменьшать метрику через удаление или quarantine без исправления причины. |
| `mean_triage_time` | Среднее время от первого падения агентного теста до классификации причины. | CI timestamps, комментарии triage, Jira/GitLab labels. | Еженедельно. | Среднее по падениям: `время классификации - время первого сигнала`. Классы: product defect, test bug, data issue, environment, known issue, flaky. | Оптимизировать только скорость, оставляя поверхностные или неверные классификации. |
| `contract_source_missing_rate` | Доля агентных тестов без зафиксированного источника контракта. | PR description, test docstrings/comments, отчёт агента, SocratiCode/OpenAPI/БД/Confluence; Jira-ссылки отдельно как traceability. | Еженедельно, обязательно на review. | `Количество агентных тестов без источника контракта / agent_generated_tests_count`. Источник должен быть конкретным: endpoint spec, таблица БД, код сервиса, требование Confluence или Graylog evidence. Jira acceptance criteria и ссылка на задачу фиксируются отдельно как provenance/traceability и не заменяют источник контракта. | Считать устное предположение или README из непроверенного репозитория достаточным контрактом. |
| `test_data_auto_created_rate` | Доля агентных тестов, где данные создаются автоматически, а не зависят от ручного стендового состояния. | Fixtures, factories, setup steps, DB/API preparation, отчёт агента. | Еженедельно. | `Количество агентных тестов с автоматической подготовкой данных / agent_generated_tests_count`. | Улучшать метрику созданием данных без cleanup, без идемпотентности или с риском загрязнения стенда. |
| `escaped_defects_after_agent_change` | Сколько дефектов ушло после принятого агентного изменения и не было поймано его тестами/review. | Production/test incidents, Jira defects, release notes, postmortem, связь с PR/MR. | Еженедельно для свежих, ежемесячно для тренда. | Количество подтверждённых escaped defects, связанных с областью агентного PR/MR после merge. | Использовать как повод запрещать агентную работу без анализа: важнее понять пропущенный контракт, данные, assertion или review gap. |

## Правила интерпретации

- Метрики читать пакетом: объём, принятие, ручная доработка, дефекты, шум, источник контракта и тестовые данные.
- Любая метрика должна вести к действию: обновить skill, уточнить роль агента, усилить review checklist, добавить fixture, улучшить triage.
- Нельзя сравнивать агентов только по raw count. Сравнение допустимо только при похожем типе задач, сложности и доступности источников.
- Метрики не должны поощрять сокрытие проблем: false positives, flaky и missing contract нужно явно показывать.
- Для спорных случаев фиксировать решение в недельном отчёте и применять одинаковое правило в следующих периодах.
