# Стратегия тестовых данных

## Цель

Документ задаёт единый поток работы с тестовыми данными для pytest-сценариев ПК АУСН: API, Kafka/categorizer, DB-проверок и внешних интеграций. Перед написанием теста агент обязан найти источник контракта и явно описать, какие данные нужны сценарию, кто их создаёт и как они изолируются при параллельном запуске `pytest -n 4`.

## Общие правила

- Источник контракта фиксируется до подготовки данных: SocratiCode, OpenAPI, исходники в `../ausn`, документация, БД или Confluence; Jira-ссылка хранится только как provenance/traceability требований.
- Каждый тест должен иметь собственную стратегию данных: статические данные допускаются только если они стабильны, не меняются тестом и не создают зависимости от порядка запуска.
- Все создаваемые тестом значения должны содержать функциональный уникальный префикс запуска: `run_id`, `worker_id` или короткое имя теста. Номер задачи не используется как часть тестовых данных.
- Тест не должен полагаться на данные, созданные другим тестом, если это не зафиксировано отдельной session/module fixture с идемпотентной подготовкой.
- Очистка выполняется через fixture finalizer, контекстный менеджер или отдельный cleanup helper. Если физическая очистка рискованна, данные должны быть идемпотентными и помеченными как тестовые.
- Для `pytest -n 4` запрещены общие изменяемые идентификаторы, общие очереди ожидания без фильтрации, фиксированные номера документов, ИНН, UUID, external IDs и Kafka keys.

## Типы тестовых данных

### Статические стендовые данные

**Когда использовать:** справочники, роли, неизменяемые настройки, заранее заведённые организации, банки, пользователи и права, которые тест только читает.

**Как создавать:** не создавать в тесте. Источник существования должен быть подтверждён запросом к БД, API, документацией стенда или fixture-проверкой перед сценарием.

**Изоляция:** тесты используют статические данные только в режиме чтения. Если сценарий меняет состояние сущности, она перестаёт быть статической и должна создаваться тестом.

**Очистка и идемпотентность:** очистка не требуется, но fixture должна проверять наличие и минимальный контракт данных. При отсутствии данных тест должен быть явно пропущен или подготовить собственный набор, если это разрешено сценарием.

**Параллельный запуск:** статические данные безопасны для `pytest -n 4`, только если не содержат счётчиков, блокировок, статусов или лимитов, которые меняются в ходе теста. Для чтения событий или логов всегда добавлять фильтр по уникальному корреляционному признаку теста.

### Данные, создаваемые тестом

**Когда использовать:** основной вариант для API и end-to-end сценариев, где тест проверяет изменение состояния.

**Как создавать:** через публичный API, factory/fixture QA-фреймворка или прямую подготовку в БД, если это подтверждено контрактом и уже принято в проекте. Значения генерируются через faker/random fixture с контролируемыми префиксами.

**Изоляция:** каждая сущность получает уникальные `external_id`, `request_id`, UUID, ИНН/КПП-подобные значения, номера документов и Kafka correlation identifiers. Не использовать фиксированные значения в payload, если поле участвует в уникальных индексах или бизнес-ключах.

**Очистка и идемпотентность:** fixture регистрирует созданные сущности и удаляет их после теста либо переводит в нейтральное состояние. Повторный запуск должен либо создать новый набор, либо безопасно переиспользовать тестовый набор по уникальному ключу без конфликта.

**Параллельный запуск:** включать `worker_id` из pytest-xdist в уникальные значения. Не хранить состояние подготовки в глобальных переменных без синхронизации. Общие session fixtures должны быть только read-only или создавать данные с lock/idempotent upsert.

### Kafka event data

**Когда использовать:** сценарии producer/consumer, categorizer, проверки обработки событий и асинхронных side effects.

**Как создавать:** публиковать событие через тестовый Kafka producer или через API, который по контракту порождает событие. Payload строить из Pydantic-модели или typed factory, чтобы схема события валидировалась до отправки.

**Изоляция:** каждое событие получает уникальные `message_id`, `event_id`, `correlation_id`, business key и Kafka key, если key влияет на partition/order. Consumer в тесте должен фильтровать сообщения по этим идентификаторам, а не читать первое подходящее сообщение из topic.

**Очистка и идемпотентность:** Kafka-события не удаляются из topic, поэтому тест должен быть идемпотентным за счёт уникальных идентификаторов и ограниченного окна ожидания. Повторный запуск не должен матчить старые сообщения.

**Параллельный запуск:** для `pytest -n 4` каждый worker использует свой уникальный prefix и consumer group, если чтение зависит от offset. При чтении общим consumer group тесты могут перехватывать события друг друга, поэтому предпочтительны worker-specific groups или чтение с фильтрацией по timestamp/correlation_id.

### DB preconditions

**Когда использовать:** когда контракт проверяется на уровне таблиц, правил, прав, справочников или состояния, недоступного через публичный API.

**Как создавать:** через SQL fixtures, repository/helper слой QA-фреймворка или idempotent setup-запросы. Перед прямой записью в БД подтвердить таблицы и ограничения через SocratiCode, миграции или схему БД.

**Изоляция:** все строки, создаваемые тестом, должны иметь тестовый маркер и уникальный business key. Для существующих строк допускается только чтение, если сценарий не владеет их жизненным циклом.

**Очистка и идемпотентность:** использовать транзакции, finalizer cleanup или idempotent upsert/delete по уникальному маркеру теста. Не выполнять широкие `DELETE` без точного фильтра по созданным данным.

**Параллельный запуск:** учитывать unique indexes, locks и sequence-dependent проверки. Для конфликтных таблиц использовать per-worker prefix, отдельные значения ключей и минимальный scope фикстур.

### External stub data

**Когда использовать:** внешние сервисы, мок-серверы, WireMock/Playwright stubs, интеграционные ответы, недоступные или нестабильные на стенде.

**Как создавать:** регистрировать stub в fixture перед тестом. Ответ должен соответствовать контракту внешнего сервиса и содержать уникальные request matchers: path, body, headers, correlation_id или query parameters.

**Изоляция:** stub не должен матчить чужие запросы. Общие wildcard-ответы допустимы только для read-only справочников и должны быть явно названы в fixture.

**Очистка и идемпотентность:** после теста удалять stub или сбрасывать mapping, если инфраструктура это поддерживает. Если сброс невозможен, matcher обязан быть уникальным для запуска.

**Параллельный запуск:** не использовать одинаковые stub keys и одинаковые broad matchers в разных тестах. Для `pytest -n 4` включать worker prefix в headers/body/query и проверять, что mock server не хранит глобальное mutable состояние между тестами.

## Правила для Kafka/categorizer

- Categorizer проверяется как Kafka consumer, а не как REST API.
- Источник правил категоризации — таблица БД `categorizer.rules`; перед тестом нужно подтвердить актуальные условия правила и ожидаемую категорию.
- В событии должны быть уникальные identifiers: `message_id`, `event_id`, `correlation_id`, ключ бизнес-сущности и тестовый prefix.
- Consumer behavior фиксируется в тесте: topic, consumer group, offset strategy, timeout, polling interval и фильтр сообщений.
- Тест не должен считать успехом появление любого похожего события. Успех — событие или side effect, связанный с уникальным identifier текущего теста.
- Если правило зависит от порядка событий, тест должен создать всю последовательность в рамках одного сценария и явно ожидать конечное состояние.
- Старые сообщения в topic считаются шумом. Фильтрация по `correlation_id`, timestamp и business key обязательна.
- Негативные сценарии проверяют отсутствие категоризации или ожидаемую ошибку в ограниченном окне ожидания, а не бесконечное ожидание.

## Правила для API

- Для позитивных сценариев использовать random fixtures/factories, которые генерируют валидные значения по контракту endpoint.
- Payload и response должны валидироваться Pydantic-моделями или существующими schema helpers. Сырые словари без валидации допустимы только для минимальных негативных payload.
- Cleanup обязателен для созданных через API сущностей, если endpoint поддерживает удаление или перевод в нейтральный статус.
- Если API не предоставляет cleanup endpoint, тестовые данные должны быть уникальными, помеченными и идемпотентными; в отчёте указать накопление данных как риск.
- Negative data строятся отдельно от позитивных fixtures: не мутировать общий валидный payload в нескольких тестах без копии.
- Негативные значения должны проверять конкретное правило контракта: тип, обязательность, формат, границы, права доступа, конфликт уникальности или недопустимый state transition.
- Для `pytest -n 4` все API-тесты, создающие состояние, используют уникальные request/correlation IDs и не зависят от порядка выполнения.

## Минимальный чек-лист агента

- Указан источник контракта.
- Для каждого теста назван тип тестовых данных.
- Создание данных выполняется через fixture/helper/API/SQL с понятным владельцем.
- Уникальность учитывает `pytest -n 4`.
- Cleanup или идемпотентность описаны явно.
- Kafka/categorizer тесты фильтруют события по уникальным identifiers.
- API-тесты используют random fixtures и Pydantic validation там, где это применимо.
