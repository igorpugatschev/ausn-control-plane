# Feedback loop QA/SDET-агентов

## Цель

Feedback loop нужен, чтобы агент не только создавал или обновлял тест, но и объяснял результат его запуска: что упало, почему это вероятно произошло, какой минимальный следующий шаг нужен и какой evidence можно передать человеку.

## Входные данные

- Plain pytest output.
- JUnit XML или Allure results, если они доступны.
- Git diff измененных тестов, fixtures и helper-кода.
- Ссылки на Graylog/Grafana/DB evidence без токенов и лишних персональных данных.
- Команда повторной проверки.

## Категории triage

- `product_bug`: поведение сервиса противоречит подтвержденному контракту.
- `test_bug`: ошибка реализации теста, helper, import, fixture wiring или assertion.
- `test_data_issue`: нет данных, данные устарели, конфликтуют или не изолированы.
- `environment_issue`: стенд, сеть, сервис, БД, Kafka, timeout или инфраструктура.
- `flaky`: результат нестабилен без изменения кода или данных.
- `contract_conflict`: источники контракта конфликтуют или фактическая схема изменилась.
- `unknown`: evidence недостаточно для уверенной классификации.

## Минимальный отчет triage

```markdown
## <pytest node id>

- Категория:
- Evidence:
- Вероятная причина:
- Следующий минимальный шаг:
- Команда повторной проверки:
- Нужен human review: да/нет
```

## Правила

- Нельзя подгонять тест под текущий ответ стенда, если он конфликтует с контрактом.
- Для `product_bug`, `contract_conflict`, `flaky` и `unknown` нужен human review.
- Для `test_data_issue` агент сначала проверяет стратегию данных из `references/test-data-strategy.md`.
- Для `environment_issue` агент фиксирует недоступность окружения и не маскирует ее как ошибку теста.
- Баг-репорт создается только по `references/bug-report-template.md`.
